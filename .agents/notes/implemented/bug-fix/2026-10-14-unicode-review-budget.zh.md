# Agent Note：Unicode 安全的 Context 审核预算

Status: implemented

[English](2026-10-14-unicode-review-budget.md) | 中文

## 问题

完整推荐投影会缩短消息内容，直到序列化 JSON 满足输入预算。原实现比较 UTF-16 长度，却按 Unicode 码点截断。含大量 emoji 的消息可能得到大于原有码点数量的截断长度，内容一直不变，导致 Host 无限等待。

## 决策

选择最长内容、检查 160 码点下限和计算每次缩减长度时，统一使用码点数量。保留序列化 JSON 预算、全部图节点身份和拓扑；仅拓扑就超过预算时仍明确拒绝。ASCII 投影行为保持一致。

Fast 候选投影也会随每个条目携带原始图顺序和广度优先距离，避免对同一次遍历生成的值再进行可空查询。分支预览提取只接受调用者已经验证的两类消息事件。外部决策、来源 URL 和图端点的校验保留。

压缩与原生来源断言复用 [tiny-invariant](https://github.com/alexreardon/tiny-invariant)，保留类型细化，并避免要求 Worker 尚不支持的 `node:assert/strict` 内置模块。原生和打包后的 Worker 部署使用同样的编译器校验。

## 考虑过的替代方案

**按 UTF-16 码元截断。** 这可能拆开代理对，产生损坏的文本。初始投影已经承诺按码点截断。

**提高输入预算。** 更长的会话仍然会遇到无法继续缩减的循环。

## 影响

每次缩减都会缩短内容，或明确拒绝剩余拓扑预算。图节点身份和最小内容下限保持稳定。码点计数会给完整投影增加有界的本地计算量；Fast 审核仍使用较小的候选包。

## 测试

回归案例构造 120 条长 emoji 消息，验证 JSON 预算、完整图保留、内容缩减和 Unicode 完整性。过大的拓扑会明确失败。其他案例覆盖不完整轮次、可见图片、重复 Deep 提交、失败提交后的纠正、清理失败和候选容量限制。全部使用本地确定性 fixture，不调用模型服务商。
