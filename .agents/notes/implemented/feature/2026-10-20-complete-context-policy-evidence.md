# Agent Note: Complete Context policy approval evidence

Status: implemented

English | [中文](2026-10-20-complete-context-policy-evidence.zh.md)

## Problem

Accepting individual Context edits does not identify a preference for complete task-owned or task-lineage preservation. A route approval can move only the draft. A parsed model policy is not user confirmation, and an existing Client can ignore newly added display fields while still submitting an ordinary approval.

## Decision

[Contextify](../../../../packages/context/contextify/README.md) attaches an optional server-built preservation descriptor to the final pending proposal. It recomputes the canonical native base after Jev: borrowed or removed source exceptions cannot acquire a pure policy label. Empty scopes, unavailable ancestry, replacements, or equal owned/lineage sets omit the descriptor. The descriptor retains the original assignment and task or new-task parent through carried Context.

A server-owned publication identity binds its display key to the exact pending review, original revisions and complete source set. The Client displays the mode and echoes only this key on an explicit full Apply or full Carry. Missing, wrong or old keys retain ordinary action behavior but produce no new policy label. The key supplies no authority and proves neither human identity nor attention. Route-only approval, partial Keep choices, unmarked calls, disabled personalization and unchanged Plans remain unlabeled.

After existing revision, manual and source checks, the Host compares the actually applied native set with the complete proposed set. A matching changed approval annotates the existing reviewed-selection event. No separate memory store or operation owner is created. Its adjacent owned node-choice and native Plan state provide Undo/Redo provenance; existing Profile watermarks remove pre-reset evidence. Inherited copies, malformed receipts and ambiguous legacy history add no examples. The projection corroborates each historical approval with its adjacent native Plan transition, accepted node modes and persisted snapshot identity, provenance and content hash. It reuses the native Plan update rule, rejects unexplained changes and leaves raw logs untouched. An inherited source alias need not equal the canonical node owner. Later ordinary edits preserve historical choices; Undo/Redo and reset still determine reuse. These checks establish local consistency rather than producer, human or global source authenticity.

Enabled Host action/goal packets and inspectable decision snapshots carry at most four complete-policy examples, each with its owning Session/event, time, mode, assignment and objective bounded to 200 Unicode code points. After proof, deduplication and retraction checks, the current objective selects up to two positive lexical matches and recent eligible cases fill remaining slots. Ties prefer recent records; output remains chronological. Empty or unmatched goals retain the recent selection. The existing multilingual Jaccard helper supplies overlap, not a learned score or applicability guarantee. Goal-specific subsets are derived per request rather than stored in the family evidence cache. Current explicit retention instructions take precedence. Only clearly applicable prior objectives may support complete preservation; conflicting or unidentifiable applicability requires abstention, and one acceptance is not a general preference. Missing or empty example lists preserve the ordinary goal request. Historical assignments do not authorize current destinations or enter answer Context. Existing ranker bonuses, thresholds, routing defaults and inference counts remain unchanged.

The existing Profile inspector exposes the latest four eligible cases through optional `ContextStewardProfile.scopePolicyExamples`. A request can retrieve older relevant cases from the same proven history, so its captured examples can differ from this recent-history view. Its panel shows historical modes, objectives and event references without another RPC or raw-message lookup. Disabled reuse does not erase inspectable history; Undo/Redo and reset update both views.

Canonical Session exports retain the original approval, Plan revisions and reset watermarks rather than only the bounded example projection. This lets a selected trace reproduce eligibility after Undo/Redo or reset without treating inactive evidence as absent history. The [management-record guide](../../../../docs/user/guide/context-steward.md#keep-a-management-record) defines selection and sharing limits.

## Alternatives considered

**Infer policies from partial masks.** Rejected because exceptions, equal source sets and manual constraints make the interpretation non-identifiable.

**Trust a proposal descriptor or Client origin without a display acknowledgement.** Rejected because older Clients can accept the same source set without displaying the new mode. A key without a publication identity also lets an old sheet label a new objective.

**Create a second persona store or learn from no-op approvals.** Rejected because native events already own the evidence, and unchanged scopes lack the same undoable Plan change used by this projection.

## Consequences

The product can retain identifiable complete-scope choices separately from partial edit examples. Engineering fixtures verify legacy compatibility, exceptions, exact pending identity, complete native scope, Carry, bounded model input, Undo/Redo, reset and disable. A real Loader fixture records an older relevant complete policy reaching the Host goal request after four unrelated approvals while Profile inspection remains recent; its request subset is pinned by an owning keyless snapshot. These establish the learning-input path, not authentic user-model accuracy, automatic Branch quality or model/answer improvements. New-task empty and unchanged scopes remain outside this projection.
